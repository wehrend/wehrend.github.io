      The evolution of HDLs (Hardware Description Languages)

      Hardware Description Languages (HDLs) and their use in modern digital design development

      After the two fundamental parts of this series - part 1 (combinational logic) and part 2 (sequential logic) - we have designed a complete CPU, from the single logic gate up to the control unit. We did this the classical way: with truth tables, boolean equations and schematics. For a full adder or a 4-bit counter this works well, but a modern processor consists of billions of transistors, and nobody draws them by hand.

      This is where Hardware Description Languages (HDLs) come in. An HDL describes a circuit as text: which signals exist, how they are connected and how the circuit behaves. At first glance, HDL code looks like a program in an ordinary programming language - but it is something fundamentally different. A program describes a sequence of steps that a processor executes one after another. An HDL describes hardware, in which all parts work at the same time.

      The same HDL description serves several purposes:

      • Documentation: the description is precise and can be read by humans and machines.

      • Simulation: we can test the circuit on the computer before it physically exists.

      • Synthesis: tools translate the description automatically into gates and flip-flops - for an FPGA or for a custom chip (ASIC).

      In this part of the series we use exactly this workflow: we describe the circuits from parts 1 and 2 in an HDL, test them in simulation and look at how they finally become hardware.

      Origins of HDLs

      The idea of describing hardware as text goes back to the 1960s. Two languages from the mid-1980s became established and still dominate today: VHDL and Verilog.

      Origins of VHDL

      VHDL goes back to the US Department of Defense. In its VHSIC program (Very High Speed Integrated Circuits), the DoD bought complex chips from many suppliers and needed a uniform way to document and simulate them. The development of the language started in 1983 by Intermetrics, IBM and Texas Instruments; the name stands for VHSIC Hardware Description Language.

      Its syntax is based on the programming language Ada, which was also used by the DoD at that time. This makes VHDL strongly typed and rather verbose - mistakes are found early, but the code is longer. In 1987 VHDL was standardized as IEEE 1076 and has been revised several times since then, most recently in 2019.

      Origins of Verilog

      Verilog was developed around 1984 by Phil Moorby at the company Gateway Design Automation - together with a simulator called Verilog-XL. Its syntax is deliberately close to the programming language C, which makes it compact and easy to learn for software developers.

      In 1989 Gateway was acquired by Cadence. Since VHDL as an open standard was gaining ground, Cadence released Verilog to the public in 1990. In 1995 Verilog became the standard IEEE 1364, followed by revisions in 2001 and 2005. Today Verilog lives on in SystemVerilog (IEEE 1800), which extends it with features for verification.

      Another important step for both languages was logic synthesis: from the end of the 1980s, tools like Synopsys Design Compiler were able to generate gate-level circuits automatically from HDL code. From that moment on, HDLs were no longer only used to describe and simulate hardware - they were used to build it.

      In this series we use Verilog, for three reasons:

      1. It is compact - the examples stay short and we can concentrate on the hardware.

      2. The open-source tools we will use - Icarus Verilog for simulation and Yosys for synthesis - are built around Verilog.

      3. If you know Verilog, the step to SystemVerilog, which is used in large parts of the chip industry, is small.

      Besides VHDL and Verilog there are also newer approaches, which generate Verilog from a modern programming language, for example Chisel (based on Scala, used for many RISC-V processors) or Amaranth (based on Python). They are worth a look once you know the basics.

      Installing the tools

      In this part of the series we use two free tools: Icarus Verilog to compile and simulate Verilog code, and a waveform viewer to look at the results. GTKWave is the classic choice; Surfer is a modern alternative that also runs directly in the browser.

      sudo pacman -S iverilog gtkwave

      brew install icarus-verilog, as viewer preferably Surfer

      Surfer is available at surfer-project.org, including a browser version that needs no installation at all.

      module hello;
    initial begin
        $display("Hello, Verilog!");
        $finish;
    end
endmodule

      Simulating a design always takes two steps: iverilog compiles the source code into a simulation file, and vvp runs it:

      $ iverilog -o hello hello.v
$ vvp hello
Hello, Verilog!
hello.v:4: $finish called at 0 (1s)

      This module is not hardware - it has no inputs, no outputs and no logic. It only uses the simulator to print a line of text. In the next chapter we will see that this is exactly how testbenches work.
