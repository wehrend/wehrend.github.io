      The Control Unit

      The Control Unit

      At the end of the post about the data path one question remained open: how do the multiplexers, the ALU, the register file and the data memory know what to do for a particular instruction? In this post the author wants to answer this question by building the last missing piece of our CPU - the control unit.

      In the post about finite state machines we have seen that the control unit of a multi-cycle CPU is a state machine. Our first CPU is a single-cycle CPU, which executes every instruction within one clock cycle. Here the control unit needs no state at all: it is pure combinational logic, as we know it from part 1. Its input is the instruction, its outputs are the control signals.

      The instruction as input

      Every RISC-V instruction is 32 bits long. The fields of the instruction are always located at the same positions, independent of the instruction format:

      The fields funct3 and funct7 distinguish instructions with the same opcode, e.g. add from sub. We will need them later for the ALU control.

      The X stands for "don’t care": for sw and beq the value of MemToReg does not matter, because RegWrite = 0 and nothing is written into the register file anyway. Such don’t cares give us freedom to make the logic smaller.

      Let’s go through the rows:

      • R-type: both operands come from registers (ALUSrc = 0), the ALU result (MemToReg = 0) is written into rd (RegWrite = 1). The ALU operation results from funct3 and funct7 (ALUOp = 10).

      • lw: the ALU adds the base register and the offset (ALUSrc = 1, ALUOp = 00), the data memory is read (MemRead = 1) and the value read is written into rd (MemToReg = 1, RegWrite = 1).

      • sw: the address is calculated like for lw, but rs2 is written to the data memory (MemWrite = 1).

      • beq: the ALU subtracts rs2 from rs1 (ALUOp = 01). If the result is zero, both registers are equal and the branch is taken (Branch = 1).

      From the table to the gates

      How do we turn this table into a circuit? The easiest way is a decoder - as in our excursion about decoders - which recognizes the four opcodes and activates exactly one of the four lines R, LW, SW and BR. Then every control signal is simply an OR of the lines in which it is 1:

      \[RegWrite = R + LW\]

      \[ALUSrc = LW + SW\]

      \[MemToReg = MemRead = LW\]

      \[MemWrite = SW\]

      \[Branch = BR\]

      \[ALUOp_1 = R \qquad ALUOp_0 = BR\]

      So the complete main control consists of a decoder for 7 bits and two OR gates. In real processors this is often implemented as a PLA (programmable logic array) or simply described in a hardware description language and left to the synthesis tool.

      Why two stages? The main control only has to make a rough decision ("address calculation", "comparison" or "look at funct"), and the ALU control does the fine decoding. Both blocks remain small, and each of them has only a few inputs. This principle of multi-level decoding keeps the logic small and fast.

      The immediate generator

      Some instructions contain a constant (immediate). The immediate generator extracts it from the instruction bits and extends it to 32 bits. Depending on the format, the bits are located at different positions:

      Format

      Used by

      Bits of the constant

      I-type

      lw, addi

      imm[11:0] = inst[31:20]

      S-type

      sw

      imm[11:5] = inst[31:25], imm[4:0] = inst[11:7]

      B-type

      beq, bne

      imm[12] = inst[31], imm[11] = inst[7], imm[10:5] = inst[30:25], imm[4:1] = inst[11:8], imm[0] = 0

      That looks a bit confusing at first, but it has a reason: wherever possible, a bit of the constant is located at the same position in all formats. And the sign bit is always inst[31]. This way the sign extension can start immediately, before the format is even known.

      For branches, the lowest bit imm[0] is always 0, since branch targets are always at an even byte address. It is therefore not stored in the instruction at all - this doubles the range of the branch.

      The sign extension fills the upper bits with copies of the sign bit. This way, a negative offset like -8 remains negative after the extension (two’s complement says hello).

      The branch decision

      For a branch the ALU computes rs1 - rs2. Its Zero output is 1, if the result is 0 - i.e. if both registers are equal. At the same time, the second adder calculates the branch target PC + offset. The multiplexer in front of the PC is controlled by:

      \[PCSrc = Branch \cdot Zero\]

      Only if the instruction is a branch and the registers are equal, the branch target is loaded into the PC. In all other cases the PC simply moves on to PC + 4.

      One instruction on its way through the CPU

      Let’s follow the instruction lw x5, 8(x6) through the picture above:

      1. The PC sends the address of the instruction to the instruction memory, which returns the instruction. At the same time, the first adder calculates PC + 4.

      2. The control unit recognizes the opcode 0000011 and sets RegWrite = 1, ALUSrc = 1, MemToReg = 1, MemRead = 1, MemWrite = 0, Branch = 0 and ALUOp = 00.

      3. The register file reads x6 (rs1). The immediate generator delivers the constant 8.

      4. Since ALUSrc = 1, the ALU receives x6 and 8. The ALU control sees ALUOp = 00 and selects addition.

      5. The ALU result x6 + 8 is the address for the data memory, which delivers the word stored there.

      6. Since MemToReg = 1, this word arrives at "Write data" of the register file.

      7. Branch = 0, so PCSrc = 0, and PC + 4 is waiting at the input of the PC.

      All of this happens within one clock cycle, as pure combinational logic. Only with the next rising clock edge, the new values are taken over: the register file writes x5, and the PC takes over PC + 4. This is exactly the behaviour of the D-flipflops from the post about clocks and registers.

      Extending the CPU: addi and bne

      Our example program from the RISC-V post uses two instructions which our minimal CPU cannot execute yet: addi and bne. Let’s extend the CPU - this shows nicely how the control unit grows with the instruction set.

      addi

      addi has its own opcode 0010011 and the I-format, like lw. It needs the constant as second ALU operand (ALUSrc = 1) and writes the ALU result into rd (MemToReg = 0, RegWrite = 1). The decoder gets a fifth line IMM:

      \[RegWrite = R + LW + IMM\]

      \[ALUSrc = LW + SW + IMM\]

      But which ALUOp? One might think of ALUOp = 10 (look at funct), since funct3 = 000 for addi. But this would be a trap: with addi there is no funct7 field - the upper bits belong to the constant. For addi x5, x5, -1 the constant consists only of ones, so bit 30 is 1 as well, and the ALU control would select subtraction! x5 - (-1) would give x5 + 1 instead of x5 - 1. So we choose ALUOp = 00, and the ALU always adds.

      bne

      bne has the same opcode as beq (1100011), they only differ in funct3: 000 for beq and 001 for bne. The lowest bit of funct3 (inst[12]) thus tells us whether the branch should be taken on equality or on inequality. We extend the branch decision by an XOR gate:

      \[PCSrc = Branch \cdot (Zero \oplus inst_{12})\]

      For beq (inst[12] = 0) the Zero signal passes unchanged, for bne (inst[12] = 1) it is inverted. The XOR works here as a controllable inverter - a trick we will meet again and again.

      And the j?

      Our program ends with j done, a pseudo instruction for jal x0, done. jal would need another opcode and an additional path for writing PC + 4 into rd. But we don’t need it: beq x0, x0, done has exactly the same effect, since x0 is always equal to itself. The branch is therefore always taken.

      Our example program, clock by clock

      With these extensions, our CPU can now execute the example program. The program is located from address 0x00 on:

      0x00:        addi x1, x0, 0       # x1 = 0   (counter)
0x04:        addi x2, x0, 1       # x2 = 1   (step)
0x08:        addi x3, x0, 10      # x3 = 10  (end value)
0x0C: loop:  add  x1, x1, x2      # x1 = x1 + x2
0x10:        sw   x1, 4(x0)       # memory[4] = x1

      After 33 clock cycles the counting is done, and the CPU circles in the endless loop at address 0x18. In clock cycle 6, for example, the ALU computes 1 - 10 = -9, so Zero = 0. Since inst[12] = 1 for bne, Zero ⊕ inst[12] = 1, and with Branch = 1 we get PCSrc = 1: the PC jumps back to 0x14 + (-8) = 0x0C.

      If you want to see this live, load the program into the simulator Ripes and select the single-cycle processor: there you can watch the control signals switch from instruction to instruction.

      Outlook

      This is where the series ends for now - but this is exactly where computer architecture really starts. Here are the most important next steps, which you will find in the literature:

      • Multi-cycle CPU: every phase gets its own clock cycle, and an instruction only uses as many cycles as it needs. The control unit becomes a state machine - exactly as described in the post about finite state machines.

      • Pipelining: the phases are separated by registers, and up to five instructions are processed at the same time, like on an assembly line. In the ideal case one instruction finishes every 200 ps instead of every 800 ps.

      • Hazards: with pipelining, problems arise: an instruction needs a result that is not yet written back (data hazard), or it is not clear yet whether a branch will be taken (control hazard). Forwarding and branch prediction help here.

      • Caches: real main memory is much slower than 200 ps. Small, fast buffer memories close to the CPU hide this.

      • Interrupts and exceptions: the CPU must be able to interrupt the current program, e.g. when a key is pressed or a division by zero occurs.

      If you want to build the CPU yourself, a hardware description language and an FPGA are the next step. The author has written some posts about getting started with FPGAs.

      Conclusion

      From the first logic gate to a CPU that runs a program: this was the path of this series. In part 1 we got to know the combinational building blocks - gates, boolean algebra, adders and the ALU. In part 2 the memory was added - flipflops, registers, memory and state machines - and finally all of this was combined into a working RISC-V CPU.
