      The CPU in Verilog

      The CPU in Verilog

      In part 2 we designed a complete single-cycle RISC-V CPU on paper: the data path in chapter 16 and the control unit in chapter 17. At the end of chapter 17 we traced our counter program clock by clock through a table - by hand.

      In the chapters since then we collected the tools to do this with a computer: modules and signals (chapter 21), testbenches and waveforms (chapter 22), vectors, hierarchy and generate (chapter 23), flip-flops and registers (chapter 24), and arithmetic in hardware (chapter 25).

      Now we put everything together. We describe the CPU in Verilog and let the simulator execute the counter program. At the end, the simulator prints the same table we filled in by hand in chapter 17.

      Tip

      All examples of this chapter are in the folder 26_cpu_verilog of our repository hdl-training, which we cloned in chapter 21: 00-register-file, 01-alu, 02-control, 03-cpu. If you cloned it earlier, git pull fetches the latest version. The README of the repository lists the command to simulate each example.

      The plan: block by block

      We could write the whole CPU in one file and simulate it. If it does not count to 10, we would have a problem: the error could be anywhere. That is why we build the CPU in four steps, and every block gets its own testbench before it is used:

      This is how chips are developed in practice as well: first every block is tested on its own (unit test), then the assembled system (integration test). If the integration test fails, we at least know that the blocks themselves are correct, and the error must be in the wiring between them.

      Step 1: The register file

      The register file holds the 32 registers x0 to x31, each 32 bits wide. In chapter 16 we drew it with three ports:

      • two read ports: the register numbers rs1 and rs2 go in, the contents rd1 and rd2 come out,

      • one write port: if RegWrite is 1, the value wd is written into register rd.

      Reading is combinational: as soon as rs1 changes, rd1 shows the new register after a short delay. Writing happens on the rising clock edge, like with every register from chapter 24. And register x0 is special: it always reads as 0, writing to it has no effect.

      // RISC-V register file: 32 registers of 32 bits,
// two read ports (combinational) and one write port (on the rising clock edge).
// Register x0 is hard-wired to 0: reading it always returns 0, writing it has no effect.
module regfile (
    input  wire        clk,
    input  wire [4:0]  rs1,         // read port 1
    input  wire [4:0]  rs2,         // read port 2
    output wire [31:0] rd1,
    output wire [31:0] rd2,
    input  wire        we,          // RegWrite
    input  wire [4:0]  rd,          // write port
    input  wire [31:0] wd
);
    reg [31:0] regs [0:31];

    assign rd1 = (rs1 == 0) ? 32'd0 : regs[rs1];
    assign rd2 = (rs2 == 0) ? 32'd0 : regs[rs2];

    always @(posedge clk)
        if (we && rd != 0)
            regs[rd] <= wd;
endmodule

      A new language feature: arrays

      So far, a signal was either a single bit or a vector like wire [31:0] a. The line

      1

      reg [31:0] regs [0:31];

      declares an array: 32 elements (the range after the name), each of them a vector of 32 bits (the range before the name). regs[5] is the complete register x5, and regs[5][31] would be its sign bit. The index does not have to be a constant: regs[rs1] selects the register whose number is currently at rs1. In hardware, this is a large multiplexer with 32 inputs of 32 bits each - and since we have two read ports, we get two of them.

      Why is x0 checked when reading?

      The write block refuses to write register 0 (rd != 0). So regs[0] is never written at all - but this also means that it is never initialized, and in simulation it contains x. That is why the read ports check for register 0 themselves and deliver a constant 0. In hardware, regs[0] does not even have to exist: the synthesis tool notices that it is never written and removes it.

module regfile_tb;
    reg         clk = 0;
    reg  [4:0]  rs1 = 0, rs2 = 0, rd = 0;
    reg         we = 0;
    reg  [31:0] wd = 0;
    wire [31:0] rd1, rd2;
    integer i, errors = 0;

    regfile dut (.clk(clk), .rs1(rs1), .rs2(rs2), .rd1(rd1), .rd2(rd2),
                 .we(we), .rd(rd), .wd(wd));

    // clock: period 10 ns
    always #5 clk = ~clk;

    initial begin
        $dumpfile("regfile.vcd");
        $dumpvars(0, regfile_tb);

        // write i * 3 into register i, and 0xDEAD into x0 (which must ignore it)
        for (i = 0; i < 32; i = i + 1) begin
            @(negedge clk);
            we = 1; rd = i; wd = (i == 0) ? 32'hDEAD : i * 3;
        end
        @(negedge clk);
        we = 0;

        // read all registers on both ports
        for (i = 0; i < 32; i = i + 1) begin
            rs1 = i; rs2 = 31 - i; #1;
            if (rd1 !== (i == 0 ? 0 : i * 3) || rd2 !== (i == 31 ? 0 : (31 - i) * 3)) begin
                errors = errors + 1;
                $display("ERROR: x%0d = %0d, x%0d = %0d", rs1, rd1, rs2, rd2);
            end
        end

        // write without we: nothing must change
        @(negedge clk);
        we = 0; rd = 5; wd = 999;
        @(negedge clk);
        rs1 = 5; #1;
        if (rd1 !== 15) begin
            errors = errors + 1;
            $display("ERROR: x5 changed without we: %0d", rd1);
        end

        rs1 = 0; rs2 = 7; #1;
        $display("x0 = %0d (0xDEAD was written, x0 stays 0), x7 = %0d", rd1, rd2);
        if (errors == 0) $display("PASSED");
        else             $display("FAILED: %0d errors", errors);
        $finish;
    end
endmodule

      The testbench first writes the value i · 3 into every register i. For x0 it tries to write 0xDEAD instead. New values are applied on the falling edge (@(negedge clk)), so they are stable at the rising edge. As in chapter 22, the inputs change away from the clock edge. Then all registers are read on both ports at the same time: port 1 counts up from x0, port 2 counts down from x31. Finally the testbench checks that nothing is written while we = 0.

      // 1-bit ALU cell from part 1 (chapter 05):
// Ainvert and Binvert invert the inputs, Operation selects the result.
//   Operation = 00: and   01: or   10: sum (add)   11: less (for slt)
module alu_cell (
    input  wire       a,
    input  wire       b,
    input  wire       ainvert,
    input  wire       binvert,
    input  wire       cin,
    input  wire       less,
    input  wire [1:0] operation,
    output reg        result,
    output wire       cout,
    output wire       sum           // needed by the most significant cell for slt
);
    wire aa = a ^ ainvert;          // the XOR as a controllable inverter
    wire bb = b ^ binvert;

    assign sum  = aa ^ bb ^ cin;    // full adder
    assign cout = (aa & bb) | (cin & (aa ^ bb));

    always @(*) begin
        case (operation)
            2'b00: result = aa & bb;
            2'b01: result = aa | bb;
            2'b10: result = sum;
            2'b11: result = less;
        endcase
    end
endmodule

      Everything in this cell is known from part 1:

      • The two XOR gates are controllable inverters: if ainvert = 1, the cell works with the inverted a. The same for b.

      • sum and cout form a full adder.

      • The case statement is the multiplexer at the output, controlled by the two Operation bits.

      • The input less is only used for slt; we will see in a moment where its value comes from.

      // N-bit ALU: a chain of 1-bit ALU cells, as in chapter 05.
// ctrl = {Ainvert, Binvert, Operation}:
//   0000 and    0001 or    0010 add    0110 sub    0111 slt    1100 nor    1101 nand
module alu #(
    parameter N = 32
) (
    input  wire [N-1:0] a,
    input  wire [N-1:0] b,
    input  wire [3:0]   ctrl,
    output wire [N-1:0] result,
    output wire         zero,
    output wire         overflow
);
    wire ainvert = ctrl[3];
    wire binvert = ctrl[2];
    wire [1:0] operation = ctrl[1:0];

    wire [N:0]   c;        // carry chain
    wire [N-1:0] sum;
    wire         is_less;   // "a < b" for slt

    // subtraction a - b = a + ~b + 1: Binvert also provides the +1 as carry in
    assign c[0] = binvert;

    genvar i;
    generate
        for (i = 0; i < N; i = i + 1) begin : slice
            alu_cell u (
                .a(a[i]), .b(b[i]),
                .ainvert(ainvert), .binvert(binvert),
                .cin(c[i]),
                .less(i == 0 ? is_less : 1'b0),   // only bit 0 gets the result of slt
                .operation(operation),
                .result(result[i]), .cout(c[i+1]), .sum(sum[i])
            );
        end
    endgenerate

    // overflow: carry into the sign bit differs from carry out of it
    assign overflow = c[N-1] ^ c[N];
    // slt: the sign of a - b, corrected if the subtraction overflowed
    assign is_less = sum[N-1] ^ overflow;
    // zero: a NOR over all result bits
    assign zero = ~|result;
endmodule

      The generate loop creates 32 copies of the cell and connects the carry output of every cell to the carry input of the next one, via the vector c. The four control bits are split up into Ainvert, Binvert and Operation. This gives us the following operations:

      Four lines deserve a closer look:

      • assign c[0] = binvert; - a subtraction is a - b = a + ~b + 1 in two’s complement. Binvert inverts b in every cell, and since Binvert is also the carry into the first cell, it provides the + 1 as well.

      • assign overflow = c[N-1] ^ c[N]; - an overflow occurs if the carry into the sign bit differs from the carry out of it.

      • assign is_less = sum[N-1] ^ overflow; - for slt the ALU computes a - b. If the result is negative, a < b. The sign bit of the sum tells us this - unless the subtraction overflowed, then the sign bit is wrong and the XOR corrects it. This value goes to the less input of cell 0. All other cells get a 0, so the result is either 1 or 0.

      • assign zero = ~|result; - the | in front of a vector is a reduction operator: it ORs all bits of the vector together. The ~ inverts the result. So zero is 1 exactly when all 32 result bits are 0 - a NOR gate with 32 inputs.

      The line with is_less might look like a loop: the result of the last cell goes back into the first cell. But it is not one: is_less depends on sum of the last cell, and sum does not depend on less at all. The signal simply runs through the carry chain once and then into the output multiplexer of cell 0. A real combinational loop, in which a signal depends on itself, would be an error.

      Note
      Why not simply write a + b?

      In practice we would: assign result = a + b; is shorter, and the synthesis tool knows very well how to build an adder, for example with the dedicated carry logic of an FPGA. Here we build the ALU from cells on purpose, because we want to see that the circuit from part 1 actually works. In chapter 27 we will see what the synthesis tool makes of it.

      `timescale 1ns / 1ps

// Tests all seven ALU operations with interesting and random values
// against the Verilog operators.
module alu_tb;
    reg  [31:0] a, b;
    reg  [3:0]  ctrl;
    wire [31:0] result;
    wire        zero, overflow;
    reg  [31:0] expected;
    integer i, k, errors = 0, tests = 0;

    alu #(.N(32)) dut (.a(a), .b(b), .ctrl(ctrl), .result(result), .zero(zero), .overflow(overflow));

    reg [3:0]  ops    [0:6];
    reg [31:0] values [0:7];

    task check;
        begin
            #1;
            case (ctrl)
                4'b0000: expected = a & b;
                4'b0001: expected = a | b;
                4'b0010: expected = a + b;
                4'b0110: expected = a - b;
                4'b0111: expected = ($signed(a) < $signed(b)) ? 1 : 0;
                4'b1100: expected = ~(a | b);
                4'b1101: expected = ~(a & b);
            endcase
            tests = tests + 1;
            if (result !== expected || zero !== (expected == 0)) begin
                errors = errors + 1;
                $display("ERROR: ctrl=%b a=%h b=%h result=%h expected=%h", ctrl, a, b, result, expected);
            end
        end
    endtask

    initial begin
        ops[0] = 4'b0000; ops[1] = 4'b0001; ops[2] = 4'b0010; ops[3] = 4'b0110;
        ops[4] = 4'b0111; ops[5] = 4'b1100; ops[6] = 4'b1101;
        // values at the edges: 0, 1, -1, largest and smallest number, ...
        values[0] = 0;            values[1] = 1;            values[2] = 32'hFFFFFFFF;
        values[3] = 32'h7FFFFFFF; values[4] = 32'h80000000; values[5] = 10;
        values[6] = 32'hFFFFFFF7; values[7] = 32'h12345678;

        // the operations of our example program
        ctrl = 4'b0010; a = 1;  b = 1;  check; $display("add: 1 + 1   = %0d", $signed(result));
        ctrl = 4'b0110; a = 1;  b = 10; check; $display("sub: 1 - 10  = %0d, zero = %b", $signed(result), zero);
        ctrl = 4'b0110; a = 10; b = 10; check; $display("sub: 10 - 10 = %0d, zero = %b", $signed(result), zero);
        // slt with overflow: -2^31 < 1, although -2^31 - 1 has a positive sign bit
        ctrl = 4'b0111; a = 32'h80000000; b = 1; check;
        $display("slt: %0d < 1 = %0d (overflow = %b)", $signed(a), result, overflow);

        for (k = 0; k < 7; k = k + 1) begin
            ctrl = ops[k];
            for (i = 0; i < 64; i = i + 1) begin
                a = values[i / 8]; b = values[i % 8]; check;
            end
            for (i = 0; i < 1000; i = i + 1) begin
                a = $random; b = $random; check;
            end
        end

        if (errors == 0) $display("PASSED: %0d tests", tests);
        else             $display("FAILED: %0d of %0d tests", errors, tests);
        $finish;
    end
endmodule

      Testing all combinations, like we did for the 8-bit shifter in chapter 25, is not possible here: with two 32-bit inputs, there are 264 combinations. Instead, the testbench uses two kinds of values:

      • Edge values: 0, 1, -1, the largest and the smallest number, and a few others. Most errors happen at the edges: at the carry from bit 30 into bit 31, at the overflow, at the transition from -1 to 0. Every operation is tested with all 64 pairs of these 8 values.

      • Random values: 1000 random pairs per operation, generated with $random. They find errors nobody thought of.

      Together with the four examples at the beginning, these are 4 + 7 · (64 + 1000) = 7452 tests. Every result is compared with the Verilog operators &, |, +, - and <:

      add: 1 + 1   = 2
sub: 1 - 10  = -9, zero = 0
sub: 10 - 10 = 0, zero = 1
slt: -2147483648 < 1 = 1 (overflow = 1)
PASSED: 7452 tests

      The last example line is the interesting one: -231 - 1 does not fit into 32 bits, the subtraction overflows, and the sign bit of the result is 0. Without the overflow correction, slt would claim that -231 is not less than 1.

      // Main control unit of the single-cycle CPU (chapter 17), pure combinational logic.
// A decoder recognizes the opcode and activates exactly one line,
// every control signal is an OR of the lines in which it is 1.
module control (
    input  wire [6:0] opcode,
    output wire       reg_write,
    output wire       alu_src,
    output wire       mem_to_reg,
    output wire       mem_read,
    output wire       mem_write,
    output wire       branch,
    output wire [1:0] alu_op
);
    // decoder: one line per instruction type
    wire r   = (opcode == 7'b0110011);   // add, sub, and, or
    wire lw  = (opcode == 7'b0000011);
    wire sw  = (opcode == 7'b0100011);
    wire br  = (opcode == 7'b1100011);   // beq, bne
    wire imm = (opcode == 7'b0010011);   // addi

    // the equations from chapter 17, including the extension for addi
    assign reg_write  = r | lw | imm;
    assign alu_src    = lw | sw | imm;
    assign mem_to_reg = lw;
    assign mem_read   = lw;
    assign mem_write  = sw;
    assign branch     = br;
    assign alu_op     = {r, br};         // ALUOp1 = R, ALUOp0 = BR
endmodule

      This is the circuit from chapter 17, one to one: a decoder with one line per instruction type, and every control signal is an OR of the lines in which it is 1. The line imm and its two ORs are the extension for addi from chapter 17. ALUOp is built with a concatenation: {r, br} puts r into bit 1 and br into bit 0.

      We could also have written the main control table as a case statement over the opcode, with one line per instruction. The result after synthesis would be the same. The form chosen here has the advantage that the code looks like the equations in chapter 17.

      // ALU control (chapter 17): the second decoding stage.
// From the 2-bit ALUOp of the main control and, for R-type instructions,
// from funct7 (only bit 30 of the instruction) and funct3, it generates
// the 4 control bits {Ainvert, Binvert, Operation} of the ALU.
module alu_control (
    input  wire [1:0] alu_op,
    input  wire       funct7_5,       // instruction bit 30
    input  wire [2:0] funct3,
    output reg  [3:0] alu_ctrl
);
    always @(*) begin
        case (alu_op)
            2'b00:   alu_ctrl = 4'b0010;                 // lw, sw, addi: add
            2'b01:   alu_ctrl = 4'b0110;                 // beq, bne: sub
            default: case (funct3)                       // R-type: look at funct
                         3'b000:  alu_ctrl = funct7_5 ? 4'b0110 : 4'b0010;   // sub / add
                         3'b111:  alu_ctrl = 4'b0000;    // and
                         3'b110:  alu_ctrl = 4'b0001;    // or
                         default: alu_ctrl = 4'b0010;
                     endcase
        endcase
    end
endmodule

      The two-stage decoding from chapter 17: ALUOp makes the rough decision, and only for R-type instructions (ALUOp = 10) funct3 and bit 30 are looked at. Note that there is a default in both case statements: as we learned in chapter 23, an always @(*) block in which an output is not assigned in every case produces a latch.

      The addi trap from chapter 17 is solved by the main control, not here: since addi gets ALUOp = 00, the ALU control never looks at bit 30 of an addi, which belongs to the constant there.

      // Immediate generator (chapter 17): extracts the constant from the instruction
// and sign-extends it to 32 bits. The sign bit is always inst[31].
module imm_gen (
    input  wire [31:0] inst,
    output reg  [31:0] imm
);
    wire [6:0] opcode = inst[6:0];

    always @(*) begin
        case (opcode)
            7'b0100011:                                          // S-type: sw
                imm = {{20{inst[31]}}, inst[31:25], inst[11:7]};
            7'b1100011:                                          // B-type: beq, bne
                imm = {{19{inst[31]}}, inst[31], inst[7], inst[30:25], inst[11:8], 1'b0};
            default:                                             // I-type: lw, addi
                imm = {{20{inst[31]}}, inst[31:20]};
        endcase
    end
endmodule

      Here the concatenation shows its strength. The table from chapter 17 can be written down almost literally: {inst[31:25], inst[11:7]} puts the two parts of the S-type constant together. {20{inst[31]}} is a replication: 20 copies of the sign bit. This is the sign extension in a single expression.

      The B-type line is the strangest one: the bits of the constant come from four places in the instruction, and a 0 is appended at the end because branch targets are always even. Counting the bits shows that it adds up: 19 + 1 + 1 + 6 + 4 + 1 = 32.

      `timescale 1ns / 1ps

// Feeds the instructions of our example program (chapter 17) into
// control, ALU control and immediate generator, and compares with the tables.
module control_tb;
    reg  [31:0] inst;
    wire        reg_write, alu_src, mem_to_reg, mem_read, mem_write, branch;
    wire [1:0]  alu_op;
    wire [3:0]  alu_ctrl;
    wire [31:0] imm;
    integer errors = 0;

    control ctl (
        .opcode(inst[6:0]), .reg_write(reg_write), .alu_src(alu_src),
        .mem_to_reg(mem_to_reg), .mem_read(mem_read), .mem_write(mem_write),
        .branch(branch), .alu_op(alu_op)
    );
    alu_control actl (.alu_op(alu_op), .funct7_5(inst[30]), .funct3(inst[14:12]), .alu_ctrl(alu_ctrl));
    imm_gen ig (.inst(inst), .imm(imm));

      // Instruction memory: 64 words, read-only, loaded from a hex file at simulation start.
// The address is a byte address; since every instruction is 4 bytes long,
// the lowest two bits are always 0 and are not used.
module instr_mem #(
    parameter PROGRAM = "program.hex"
) (
    input  wire [31:0] addr,
    output wire [31:0] inst
);
    reg [31:0] mem [0:63];

    initial $readmemh(PROGRAM, mem);

    assign inst = mem[addr[7:2]];
endmodule

      The instruction memory is an array of 64 words. $readmemh loads it from a text file with hexadecimal numbers when the simulation starts - one instruction per line:

      // Example program from chapters 15 and 17: counts from 1 to 10
// and writes every value to data memory address 4.
// One instruction (32 bit) per line, starting at address 0x00.
00000093  // 0x00:        addi x1, x0, 0      x1 = 0  (counter)
00100113  // 0x04:        addi x2, x0, 1      x2 = 1  (step)
00a00193  // 0x08:        addi x3, x0, 10     x3 = 10 (end value)

      // Data memory: 64 words. Reading is combinational (MemRead),
// writing happens on the rising clock edge (MemWrite).
module data_mem (
    input  wire        clk,
    input  wire [31:0] addr,
    input  wire        mem_read,
    input  wire        mem_write,
    input  wire [31:0] wd,
    output wire [31:0] rd
);
    reg [31:0] mem [0:63];

    integer i;
    initial for (i = 0; i < 64; i = i + 1) mem[i] = 0;

    assign rd = mem_read ? mem[addr[7:2]] : 32'd0;

    always @(posedge clk)
        if (mem_write)
            mem[addr[7:2]] <= wd;
endmodule

      The data memory works like the register file, just with one port: reading is combinational, writing happens on the rising edge if MemWrite = 1. The initial loop sets all words to 0 at the beginning of the simulation, so we do not see x in the waveform.

      // Single-cycle RISC-V CPU from part 2 (chapters 16 and 17).
// Instructions: add, sub, and, or, addi, lw, sw, beq, bne.
// Every instruction is executed in one clock cycle: everything between two
// rising edges is combinational logic, only PC, register file and data memory store values.
module cpu #(
    parameter PROGRAM = "program.hex"
) (
    input  wire clk,
    input  wire rst
);
    // ---- instruction fetch -------------------------------------------------
    reg  [31:0] pc;
    wire [31:0] inst;
    wire [31:0] pc_plus4 = pc + 4;               // first adder

    instr_mem #(.PROGRAM(PROGRAM)) imem (.addr(pc), .inst(inst));

    // ---- decode: the fields of the instruction ----------------------------
    wire [6:0] opcode = inst[6:0];
    wire [4:0] rd     = inst[11:7];
    wire [2:0] funct3 = inst[14:12];
    wire [4:0] rs1    = inst[19:15];
    wire [4:0] rs2    = inst[24:20];

    // ---- control ------------------------------------------------------------
    wire       reg_write, alu_src, mem_to_reg, mem_read, mem_write, branch;
    wire [1:0] alu_op;
    wire [3:0] alu_ctrl;

    control ctl (
        .opcode(opcode), .reg_write(reg_write), .alu_src(alu_src),
        .mem_to_reg(mem_to_reg), .mem_read(mem_read), .mem_write(mem_write),
        .branch(branch), .alu_op(alu_op)
    );
    alu_control actl (.alu_op(alu_op), .funct7_5(inst[30]), .funct3(funct3), .alu_ctrl(alu_ctrl));

    // ---- register file and immediate ---------------------------------------
    wire [31:0] rd1, rd2, imm, write_data;

    regfile rf (
        .clk(clk), .rs1(rs1), .rs2(rs2), .rd1(rd1), .rd2(rd2),
        .we(reg_write), .rd(rd), .wd(write_data)
    );
    imm_gen ig (.inst(inst), .imm(imm));

    // ---- execute -------------------------------------------------------------
    wire [31:0] alu_b = alu_src ? imm : rd2;     // multiplexer in front of the ALU
    wire [31:0] alu_result;
    wire        zero, overflow;

    alu #(.N(32)) alu (
        .a(rd1), .b(alu_b), .ctrl(alu_ctrl),
        .result(alu_result), .zero(zero), .overflow(overflow)
    );

    // ---- memory access ---------------------------------------------------------
    wire [31:0] mem_data;

    data_mem dmem (
        .clk(clk), .addr(alu_result), .mem_read(mem_read), .mem_write(mem_write),
        .wd(rd2), .rd(mem_data)
    );

    // ---- write back ------------------------------------------------------------
    assign write_data = mem_to_reg ? mem_data : alu_result;   // multiplexer behind the memory

    // ---- next PC ---------------------------------------------------------------
    wire [31:0] branch_target = pc + imm;                     // second adder
    wire        pc_src = branch & (zero ^ inst[12]);          // inst[12] = 1 for bne
    wire [31:0] pc_next = pc_src ? branch_target : pc_plus4;  // multiplexer in front of the PC

    always @(posedge clk)
        if (rst) pc <= 0;
        else     pc <= pc_next;
endmodule

      If you hold the picture from chapter 17 next to this code, you will find every block and every wire. The code is ordered like the phases of an instruction:

      • Instruction fetch: the PC addresses the instruction memory, the first adder computes PC + 4.

      • Decode: the instruction is cut into its fields. These are just wires, no logic: inst[19:15] is rs1.

      • Control: main control and ALU control generate the control signals.

      • Register file and immediate: the register file reads rs1 and rs2, the immediate generator extracts the constant.

      • Execute: the multiplexer in front of the ALU selects the second operand, the ALU computes.

      • Memory access: the ALU result is the address for the data memory, rs2 is the data to write.

      • Write back: the multiplexer behind the memory selects what is written into rd.

      • Next PC: the second adder computes the branch target, PCSrc selects the next PC.

      All multiplexers are a single line with the conditional operator from chapter 24, for example alu_b = alu_src ? imm : rd2. And the branch decision with the extension for bne is the formula from chapter 17:

      \[PCSrc = Branch \cdot (Zero \oplus inst_{12})\]

      In the whole module, there is only one always block: the PC. Together with the register file and the data memory, it is the only part of the CPU that stores anything. Everything else is combinational logic between two clock edges - this is exactly what "single-cycle" means.

      The PC has a synchronous reset: as long as rst = 1, the PC is set to 0 at every rising edge. Without a reset, the PC would start with x, and the CPU would fetch an instruction from an unknown address.

    // At the rising edge, the non-blocking assignments have not happened yet:
    // we still see the instruction of this cycle and the values that are about to be stored.
    always @(posedge clk)
        if (!rst) begin
            cycle = cycle + 1;
            $write("clock %2d  PC=0x%02h  inst=%h  ", cycle, dut.pc[7:0], dut.inst);
            if (dut.reg_write) $write("x%0d = %0d", dut.rd, $signed(dut.write_data));
            if (dut.mem_write) $write("memory[%0d] = %0d", dut.alu_result, dut.rd2);
            if (dut.branch)    $write("Zero=%b PCSrc=%b", dut.zero, dut.pc_src);
            $display("  ->  next PC=0x%02h", dut.pc_next[7:0]);

                writes = writes + 1;
                if (dut.rd2 !== writes) begin

      The testbench does three things:

      • It generates the clock and releases the reset after 12 ns.

      • At every rising edge it prints one line: PC, instruction and what the instruction does. At the rising edge the new values are not stored yet (they are non-blocking assignments, see chapter 24), so we still see the instruction of this cycle and the value that is about to be written.

      • After 35 clock cycles it checks the result: x1 and x3 must be 10, memory[4] must be 10, the PC must be at 0x18, and there must have been exactly 10 writes to the memory, with the values 1 to 10.

      The testbench looks into the CPU with hierarchical names: dut.rf.regs[1] is element 1 of the array regs in the instance rf inside the instance dut. This only works in simulation, a synthesis tool would reject it. But for a testbench, it is very handy: we can watch any signal without having to lead it out of the CPU through ports.

      Simulation is not hardware (yet)

      Our CPU works - in simulation. Can we now load it onto an FPGA? We tried it with the Lattice iCE40 HX1K, the FPGA on the Nandland Go Board, which we will use in the next chapter. The result: the design needs more than three times as many logic cells as the chip has.

      The reason lies in the memories. Register file and data memory are read combinationally. The FPGA has fast block RAM, but block RAM can only be read on a clock edge. So the synthesis tool builds our memories from single flip-flops and huge multiplexers - more than 3000 flip-flops just for storage. In simulation, this makes no difference at all.

      How to fix this, and what happens between the Verilog code and the chip - synthesis, place and route, timing analysis - is the topic of chapter 27.

      Summary

      • We built the single-cycle CPU from part 2 in Verilog, from four kinds of blocks: register file, ALU, control (main control, ALU control, immediate generator) and memories.

      • Every block got its own testbench before it was used. The CPU testbench then only had to check the wiring.

      • New language features: arrays (reg [31:0] regs [0:31]), the reduction operator (~|result), replication ({20{inst[31]}}), $readmemh for loading memory contents, and hierarchical names in testbenches.

      • The CPU executes our counter program in 33 clock cycles - exactly as we predicted by hand in chapter 17.

      • What works in simulation does not automatically fit onto a chip. That is the topic of the next chapter.
