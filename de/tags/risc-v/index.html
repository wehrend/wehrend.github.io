      Schritt 1: Die Registerdatei

      Die Registerdatei enthält die 32 Register x0 bis x31, jedes 32 Bit breit. In Kapitel 16 haben wir sie mit drei Anschlüssen gezeichnet:

      • zwei Leseports: Die Registernummern rs1 und rs2 gehen hinein, die Inhalte rd1 und rd2 kommen heraus,

      • ein Schreibport: Ist RegWrite gleich 1, wird der Wert wd in das Register rd geschrieben.

      Das Lesen ist kombinatorisch: Sobald sich rs1 ändert, zeigt rd1 nach einer kurzen Verzögerung das neue Register. Geschrieben wird mit der steigenden Taktflanke, wie bei jedem Register aus Kapitel 24. Und das Register x0 ist etwas Besonderes: Es liefert beim Lesen immer 0, Schreiben hat keine Wirkung.

      // RISC-V register file: 32 registers of 32 bits,
// two read ports (combinational) and one write port (on the rising clock edge).
// Register x0 is hard-wired to 0: reading it always returns 0, writing it has no effect.
module regfile (
    input  wire        clk,
    input  wire [4:0]  rs1,         // read port 1
    input  wire [4:0]  rs2,         // read port 2
    output wire [31:0] rd1,
    output wire [31:0] rd2,
    input  wire        we,          // RegWrite
    input  wire [4:0]  rd,          // write port
    input  wire [31:0] wd
);
    reg [31:0] regs [0:31];

    assign rd1 = (rs1 == 0) ? 32'd0 : regs[rs1];
    assign rd2 = (rs2 == 0) ? 32'd0 : regs[rs2];

    always @(posedge clk)
        if (we && rd != 0)
            regs[rd] <= wd;
endmodule

      Ein neues Sprachmittel: Arrays

      Bisher war ein Signal entweder ein einzelnes Bit oder ein Vektor wie wire [31:0] a. Die Zeile

      1

      reg [31:0] regs [0:31];

      deklariert ein Array: 32 Elemente (der Bereich nach dem Namen), jedes davon ein Vektor aus 32 Bit (der Bereich vor dem Namen). regs[5] ist das komplette Register x5, und regs[5][31] wäre sein Vorzeichenbit. Der Index muss keine Konstante sein: regs[rs1] wählt das Register aus, dessen Nummer gerade an rs1 anliegt. In Hardware ist das ein großer Multiplexer mit 32 Eingängen zu je 32 Bit - und da wir zwei Leseports haben, bekommen wir zwei davon.

      Warum wird x0 beim Lesen abgefragt?

      Der Schreibblock weigert sich, Register 0 zu beschreiben (rd != 0). regs[0] wird also nie beschrieben - das bedeutet aber auch, dass es nie initialisiert wird und in der Simulation x enthält. Deshalb prüfen die Leseports selbst auf Register 0 und liefern eine konstante 0. In Hardware muss regs[0] gar nicht existieren: Das Synthesewerkzeug bemerkt, dass es nie beschrieben wird, und entfernt es.

module regfile_tb;
    reg         clk = 0;
    reg  [4:0]  rs1 = 0, rs2 = 0, rd = 0;
    reg         we = 0;
    reg  [31:0] wd = 0;
    wire [31:0] rd1, rd2;
    integer i, errors = 0;

    regfile dut (.clk(clk), .rs1(rs1), .rs2(rs2), .rd1(rd1), .rd2(rd2),
                 .we(we), .rd(rd), .wd(wd));

    // clock: period 10 ns
    always #5 clk = ~clk;

    initial begin
        $dumpfile("regfile.vcd");
        $dumpvars(0, regfile_tb);

        // write i * 3 into register i, and 0xDEAD into x0 (which must ignore it)
        for (i = 0; i < 32; i = i + 1) begin
            @(negedge clk);
            we = 1; rd = i; wd = (i == 0) ? 32'hDEAD : i * 3;
        end
        @(negedge clk);
        we = 0;

        // read all registers on both ports
        for (i = 0; i < 32; i = i + 1) begin
            rs1 = i; rs2 = 31 - i; #1;
            if (rd1 !== (i == 0 ? 0 : i * 3) || rd2 !== (i == 31 ? 0 : (31 - i) * 3)) begin
                errors = errors + 1;
                $display("ERROR: x%0d = %0d, x%0d = %0d", rs1, rd1, rs2, rd2);
            end
        end

        // write without we: nothing must change
        @(negedge clk);
        we = 0; rd = 5; wd = 999;
        @(negedge clk);
        rs1 = 5; #1;
        if (rd1 !== 15) begin
            errors = errors + 1;
            $display("ERROR: x5 changed without we: %0d", rd1);
        end

        rs1 = 0; rs2 = 7; #1;
        $display("x0 = %0d (0xDEAD was written, x0 stays 0), x7 = %0d", rd1, rd2);
        if (errors == 0) $display("PASSED");
        else             $display("FAILED: %0d errors", errors);
        $finish;
    end
endmodule

      Die Testbench schreibt zuerst den Wert i · 3 in jedes Register i. Bei x0 versucht sie stattdessen, 0xDEAD zu schreiben. Neue Werte werden an der fallenden Flanke angelegt (@(negedge clk)), damit sie an der steigenden Flanke stabil sind. Wie in Kapitel 22 ändern sich die Eingänge also nicht genau an der Taktflanke. Dann werden alle Register gleichzeitig über beide Ports gelesen: Port 1 zählt von x0 aufwärts, Port 2 von x31 abwärts. Zum Schluss prüft die Testbench, dass bei we = 0 nichts geschrieben wird.

      // 1-bit ALU cell from part 1 (chapter 05):
// Ainvert and Binvert invert the inputs, Operation selects the result.
//   Operation = 00: and   01: or   10: sum (add)   11: less (for slt)
module alu_cell (
    input  wire       a,
    input  wire       b,
    input  wire       ainvert,
    input  wire       binvert,
    input  wire       cin,
    input  wire       less,
    input  wire [1:0] operation,
    output reg        result,
    output wire       cout,
    output wire       sum           // needed by the most significant cell for slt
);
    wire aa = a ^ ainvert;          // the XOR as a controllable inverter
    wire bb = b ^ binvert;

    assign sum  = aa ^ bb ^ cin;    // full adder
    assign cout = (aa & bb) | (cin & (aa ^ bb));

    always @(*) begin
        case (operation)
            2'b00: result = aa & bb;
            2'b01: result = aa | bb;
            2'b10: result = sum;
            2'b11: result = less;
        endcase
    end
endmodule

      Alles in dieser Zelle kennen wir aus Teil 1:

      • Die beiden XOR-Gatter sind steuerbare Inverter: Ist ainvert = 1, arbeitet die Zelle mit dem invertierten a. Dasselbe gilt für b.

      • sum und cout bilden einen Volladdierer.

      • Die case-Anweisung ist der Multiplexer am Ausgang, gesteuert von den beiden Operation-Bits.

      • Der Eingang less wird nur für slt gebraucht; woher sein Wert kommt, sehen wir gleich.

      // N-bit ALU: a chain of 1-bit ALU cells, as in chapter 05.
// ctrl = {Ainvert, Binvert, Operation}:
//   0000 and    0001 or    0010 add    0110 sub    0111 slt    1100 nor    1101 nand
module alu #(
    parameter N = 32
) (
    input  wire [N-1:0] a,
    input  wire [N-1:0] b,
    input  wire [3:0]   ctrl,
    output wire [N-1:0] result,
    output wire         zero,
    output wire         overflow
);
    wire ainvert = ctrl[3];
    wire binvert = ctrl[2];
    wire [1:0] operation = ctrl[1:0];

    wire [N:0]   c;        // carry chain
    wire [N-1:0] sum;
    wire         is_less;   // "a < b" for slt

    // subtraction a - b = a + ~b + 1: Binvert also provides the +1 as carry in
    assign c[0] = binvert;

    genvar i;
    generate
        for (i = 0; i < N; i = i + 1) begin : slice
            alu_cell u (
                .a(a[i]), .b(b[i]),
                .ainvert(ainvert), .binvert(binvert),
                .cin(c[i]),
                .less(i == 0 ? is_less : 1'b0),   // only bit 0 gets the result of slt
                .operation(operation),
                .result(result[i]), .cout(c[i+1]), .sum(sum[i])
            );
        end
    endgenerate

    // overflow: carry into the sign bit differs from carry out of it
    assign overflow = c[N-1] ^ c[N];
    // slt: the sign of a - b, corrected if the subtraction overflowed
    assign is_less = sum[N-1] ^ overflow;
    // zero: a NOR over all result bits
    assign zero = ~|result;
endmodule

      Die generate-Schleife erzeugt 32 Kopien der Zelle und verbindet über den Vektor c den Übertragsausgang jeder Zelle mit dem Übertragseingang der nächsten. Die vier Steuerbits werden in Ainvert, Binvert und Operation aufgeteilt. Damit ergeben sich folgende Operationen:

      Vier Zeilen verdienen einen genaueren Blick:

      • assign c[0] = binvert; - im Zweierkomplement ist eine Subtraktion a - b = a + ~b + 1. Binvert invertiert b in jeder Zelle, und da Binvert zugleich der Übertrag in die erste Zelle ist, liefert es auch gleich die + 1.

      • assign overflow = c[N-1] ^ c[N]; - ein Überlauf liegt vor, wenn sich der Übertrag in das Vorzeichenbit vom Übertrag aus ihm heraus unterscheidet.

      • assign is_less = sum[N-1] ^ overflow; - für slt berechnet die ALU a - b. Ist das Ergebnis negativ, gilt a < b. Das verrät uns das Vorzeichenbit der Summe - außer die Subtraktion ist übergelaufen, dann ist das Vorzeichenbit falsch und das XOR korrigiert es. Dieser Wert geht an den Eingang less von Zelle 0. Alle anderen Zellen bekommen eine 0, das Ergebnis ist also entweder 1 oder 0.

      • assign zero = ~|result; - das | vor einem Vektor ist ein Reduktionsoperator: Er verknüpft alle Bits des Vektors mit ODER. Das ~ invertiert das Ergebnis. zero ist also genau dann 1, wenn alle 32 Ergebnisbits 0 sind - ein NOR-Gatter mit 32 Eingängen.

      Die Zeile mit is_less sieht vielleicht wie eine Schleife aus: Das Ergebnis der letzten Zelle geht zurück in die erste Zelle. Sie ist aber keine: is_less hängt von sum der letzten Zelle ab, und sum hängt überhaupt nicht von less ab. Das Signal läuft einfach einmal durch die Übertragskette und dann in den Ausgangsmultiplexer von Zelle 0. Eine echte kombinatorische Schleife, in der ein Signal von sich selbst abhängt, wäre ein Fehler.

      Note
      Warum nicht einfach a + b schreiben?

      In der Praxis würden wir das tun: assign result = a + b; ist kürzer, und das Synthesewerkzeug weiß sehr gut, wie man einen Addierer baut, zum Beispiel mit der eigens dafür vorhandenen Übertragslogik eines FPGAs. Hier bauen wir die ALU absichtlich aus Zellen, weil wir sehen wollen, dass die Schaltung aus Teil 1 tatsächlich funktioniert. In Kapitel 27 sehen wir uns an, was das Synthesewerkzeug daraus macht.

      `timescale 1ns / 1ps

// Tests all seven ALU operations with interesting and random values
// against the Verilog operators.
module alu_tb;
    reg  [31:0] a, b;
    reg  [3:0]  ctrl;
    wire [31:0] result;
    wire        zero, overflow;
    reg  [31:0] expected;
    integer i, k, errors = 0, tests = 0;

    alu #(.N(32)) dut (.a(a), .b(b), .ctrl(ctrl), .result(result), .zero(zero), .overflow(overflow));

    reg [3:0]  ops    [0:6];
    reg [31:0] values [0:7];

    task check;
        begin
            #1;
            case (ctrl)
                4'b0000: expected = a & b;
                4'b0001: expected = a | b;
                4'b0010: expected = a + b;
                4'b0110: expected = a - b;
                4'b0111: expected = ($signed(a) < $signed(b)) ? 1 : 0;
                4'b1100: expected = ~(a | b);
                4'b1101: expected = ~(a & b);
            endcase
            tests = tests + 1;
            if (result !== expected || zero !== (expected == 0)) begin
                errors = errors + 1;
                $display("ERROR: ctrl=%b a=%h b=%h result=%h expected=%h", ctrl, a, b, result, expected);
            end
        end
    endtask

    initial begin
        ops[0] = 4'b0000; ops[1] = 4'b0001; ops[2] = 4'b0010; ops[3] = 4'b0110;
        ops[4] = 4'b0111; ops[5] = 4'b1100; ops[6] = 4'b1101;
        // values at the edges: 0, 1, -1, largest and smallest number, ...
        values[0] = 0;            values[1] = 1;            values[2] = 32'hFFFFFFFF;
        values[3] = 32'h7FFFFFFF; values[4] = 32'h80000000; values[5] = 10;
        values[6] = 32'hFFFFFFF7; values[7] = 32'h12345678;

        // the operations of our example program
        ctrl = 4'b0010; a = 1;  b = 1;  check; $display("add: 1 + 1   = %0d", $signed(result));
        ctrl = 4'b0110; a = 1;  b = 10; check; $display("sub: 1 - 10  = %0d, zero = %b", $signed(result), zero);
        ctrl = 4'b0110; a = 10; b = 10; check; $display("sub: 10 - 10 = %0d, zero = %b", $signed(result), zero);
        // slt with overflow: -2^31 < 1, although -2^31 - 1 has a positive sign bit
        ctrl = 4'b0111; a = 32'h80000000; b = 1; check;
        $display("slt: %0d < 1 = %0d (overflow = %b)", $signed(a), result, overflow);

        for (k = 0; k < 7; k = k + 1) begin
            ctrl = ops[k];
            for (i = 0; i < 64; i = i + 1) begin
                a = values[i / 8]; b = values[i % 8]; check;
            end
            for (i = 0; i < 1000; i = i + 1) begin
                a = $random; b = $random; check;
            end
        end

        if (errors == 0) $display("PASSED: %0d tests", tests);
        else             $display("FAILED: %0d of %0d tests", errors, tests);
        $finish;
    end
endmodule

      Alle Kombinationen zu testen, wie beim 8-Bit-Shifter in Kapitel 25, ist hier nicht möglich: Bei zwei 32-Bit-Eingängen gibt es 264 Kombinationen. Stattdessen verwendet die Testbench zwei Arten von Werten:

      • Randwerte: 0, 1, -1, die größte und die kleinste Zahl und ein paar weitere. Die meisten Fehler passieren an den Rändern: beim Übertrag von Bit 30 in Bit 31, beim Überlauf, beim Übergang von -1 auf 0. Jede Operation wird mit allen 64 Paaren aus diesen 8 Werten getestet.

      • Zufallswerte: 1000 zufällige Paare pro Operation, erzeugt mit $random. Sie finden Fehler, an die niemand gedacht hat.

      Zusammen mit den vier Beispielen am Anfang sind das 4 + 7 · (64 + 1000) = 7452 Tests. Jedes Ergebnis wird mit den Verilog-Operatoren &, |, +, - und < verglichen:

      add: 1 + 1   = 2
sub: 1 - 10  = -9, zero = 0
sub: 10 - 10 = 0, zero = 1
slt: -2147483648 < 1 = 1 (overflow = 1)
PASSED: 7452 tests

      Interessant ist die letzte Beispielzeile: -231 - 1 passt nicht in 32 Bit, die Subtraktion läuft über, und das Vorzeichenbit des Ergebnisses ist 0. Ohne die Überlaufkorrektur würde slt behaupten, -231 sei nicht kleiner als 1.

      // Main control unit of the single-cycle CPU (chapter 17), pure combinational logic.
// A decoder recognizes the opcode and activates exactly one line,
// every control signal is an OR of the lines in which it is 1.
module control (
    input  wire [6:0] opcode,
    output wire       reg_write,
    output wire       alu_src,
    output wire       mem_to_reg,
    output wire       mem_read,
    output wire       mem_write,
    output wire       branch,
    output wire [1:0] alu_op
);
    // decoder: one line per instruction type
    wire r   = (opcode == 7'b0110011);   // add, sub, and, or
    wire lw  = (opcode == 7'b0000011);
    wire sw  = (opcode == 7'b0100011);
    wire br  = (opcode == 7'b1100011);   // beq, bne
    wire imm = (opcode == 7'b0010011);   // addi

    // the equations from chapter 17, including the extension for addi
    assign reg_write  = r | lw | imm;
    assign alu_src    = lw | sw | imm;
    assign mem_to_reg = lw;
    assign mem_read   = lw;
    assign mem_write  = sw;
    assign branch     = br;
    assign alu_op     = {r, br};         // ALUOp1 = R, ALUOp0 = BR
endmodule

      Das ist die Schaltung aus Kapitel 17, eins zu eins: ein Decoder mit einer Leitung pro Befehlstyp, und jedes Steuersignal ist ein ODER der Leitungen, in denen es 1 ist. Die Leitung imm und ihre beiden ODER sind die Erweiterung für addi aus Kapitel 17. ALUOp entsteht durch eine Verkettung: {r, br} legt r in Bit 1 und br in Bit 0.

      Wir hätten die Haupttabelle auch als case-Anweisung über den Opcode schreiben können, mit einer Zeile pro Befehl. Nach der Synthese käme dasselbe heraus. Die hier gewählte Form hat den Vorteil, dass der Code aussieht wie die Gleichungen in Kapitel 17.

      // ALU control (chapter 17): the second decoding stage.
// From the 2-bit ALUOp of the main control and, for R-type instructions,
// from funct7 (only bit 30 of the instruction) and funct3, it generates
// the 4 control bits {Ainvert, Binvert, Operation} of the ALU.
module alu_control (
    input  wire [1:0] alu_op,
    input  wire       funct7_5,       // instruction bit 30
    input  wire [2:0] funct3,
    output reg  [3:0] alu_ctrl
);
    always @(*) begin
        case (alu_op)
            2'b00:   alu_ctrl = 4'b0010;                 // lw, sw, addi: add
            2'b01:   alu_ctrl = 4'b0110;                 // beq, bne: sub
            default: case (funct3)                       // R-type: look at funct
                         3'b000:  alu_ctrl = funct7_5 ? 4'b0110 : 4'b0010;   // sub / add
                         3'b111:  alu_ctrl = 4'b0000;    // and
                         3'b110:  alu_ctrl = 4'b0001;    // or
                         default: alu_ctrl = 4'b0010;
                     endcase
        endcase
    end
endmodule

      Die zweistufige Decodierung aus Kapitel 17: ALUOp trifft die grobe Entscheidung, und nur bei R-Typ-Befehlen (ALUOp = 10) werden funct3 und Bit 30 angesehen. Beachte, dass beide case-Anweisungen ein default haben: Wie wir in Kapitel 23 gelernt haben, erzeugt ein always @(*)-Block, in dem ein Ausgang nicht in jedem Fall zugewiesen wird, ein Latch.

      // Immediate generator (chapter 17): extracts the constant from the instruction
// and sign-extends it to 32 bits. The sign bit is always inst[31].
module imm_gen (
    input  wire [31:0] inst,
    output reg  [31:0] imm
);
    wire [6:0] opcode = inst[6:0];

    always @(*) begin
        case (opcode)
            7'b0100011:                                          // S-type: sw
                imm = {{20{inst[31]}}, inst[31:25], inst[11:7]};
            7'b1100011:                                          // B-type: beq, bne
                imm = {{19{inst[31]}}, inst[31], inst[7], inst[30:25], inst[11:8], 1'b0};
            default:                                             // I-type: lw, addi
                imm = {{20{inst[31]}}, inst[31:20]};
        endcase
    end
endmodule

      Hier zeigt die Verkettung ihre Stärke. Die Tabelle aus Kapitel 17 lässt sich fast wörtlich hinschreiben: {inst[31:25], inst[11:7]} setzt die beiden Teile der S-Typ-Konstanten zusammen. {20{inst[31]}} ist eine Replikation: 20 Kopien des Vorzeichenbits. Das ist die Vorzeichenerweiterung in einem einzigen Ausdruck.

      // Single-cycle RISC-V CPU from part 2 (chapters 16 and 17).
// Instructions: add, sub, and, or, addi, lw, sw, beq, bne.
// Every instruction is executed in one clock cycle: everything between two
// rising edges is combinational logic, only PC, register file and data memory store values.
module cpu #(
    parameter PROGRAM = "program.hex"
) (
    input  wire clk,
    input  wire rst
);
    // ---- instruction fetch -------------------------------------------------
    reg  [31:0] pc;
    wire [31:0] inst;
    wire [31:0] pc_plus4 = pc + 4;               // first adder

    instr_mem #(.PROGRAM(PROGRAM)) imem (.addr(pc), .inst(inst));

    // ---- decode: the fields of the instruction ----------------------------
    wire [6:0] opcode = inst[6:0];
    wire [4:0] rd     = inst[11:7];
    wire [2:0] funct3 = inst[14:12];
    wire [4:0] rs1    = inst[19:15];
    wire [4:0] rs2    = inst[24:20];

    // ---- control ------------------------------------------------------------
    wire       reg_write, alu_src, mem_to_reg, mem_read, mem_write, branch;
    wire [1:0] alu_op;
    wire [3:0] alu_ctrl;

    control ctl (
        .opcode(opcode), .reg_write(reg_write), .alu_src(alu_src),
        .mem_to_reg(mem_to_reg), .mem_read(mem_read), .mem_write(mem_write),
        .branch(branch), .alu_op(alu_op)
    );
    alu_control actl (.alu_op(alu_op), .funct7_5(inst[30]), .funct3(funct3), .alu_ctrl(alu_ctrl));

    // ---- register file and immediate ---------------------------------------
    wire [31:0] rd1, rd2, imm, write_data;

    regfile rf (
        .clk(clk), .rs1(rs1), .rs2(rs2), .rd1(rd1), .rd2(rd2),
        .we(reg_write), .rd(rd), .wd(write_data)
    );
    imm_gen ig (.inst(inst), .imm(imm));

    // ---- execute -------------------------------------------------------------
    wire [31:0] alu_b = alu_src ? imm : rd2;     // multiplexer in front of the ALU
    wire [31:0] alu_result;
    wire        zero, overflow;

    alu #(.N(32)) alu (
        .a(rd1), .b(alu_b), .ctrl(alu_ctrl),
        .result(alu_result), .zero(zero), .overflow(overflow)
    );

    // ---- memory access ---------------------------------------------------------
    wire [31:0] mem_data;

    data_mem dmem (
        .clk(clk), .addr(alu_result), .mem_read(mem_read), .mem_write(mem_write),
        .wd(rd2), .rd(mem_data)
    );

    // ---- write back ------------------------------------------------------------
    assign write_data = mem_to_reg ? mem_data : alu_result;   // multiplexer behind the memory

    // ---- next PC ---------------------------------------------------------------
    wire [31:0] branch_target = pc + imm;                     // second adder
    wire        pc_src = branch & (zero ^ inst[12]);          // inst[12] = 1 for bne
    wire [31:0] pc_next = pc_src ? branch_target : pc_plus4;  // multiplexer in front of the PC

    always @(posedge clk)
        if (rst) pc <= 0;
        else     pc <= pc_next;
endmodule

      Wer das Bild aus Kapitel 17 neben diesen Code legt, findet jeden Block und jede Leitung wieder. Der Code ist nach den Phasen eines Befehls geordnet:

      • Befehl holen: Der PC adressiert den Befehlsspeicher, der erste Addierer berechnet PC + 4.

      • Decodieren: Der Befehl wird in seine Felder zerlegt. Das sind nur Leitungen, keine Logik: inst[19:15] ist rs1.

      • Steuerung: Hauptsteuerwerk und ALU-Steuerung erzeugen die Steuersignale.

      • Registerdatei und Immediate: Die Registerdatei liest rs1 und rs2, der Immediate-Generator holt die Konstante heraus.

      • Ausführen: Der Multiplexer vor der ALU wählt den zweiten Operanden, die ALU rechnet.

      • Speicherzugriff: Das ALU-Ergebnis ist die Adresse für den Datenspeicher, rs2 sind die zu schreibenden Daten.

      • Zurückschreiben: Der Multiplexer hinter dem Speicher wählt aus, was in rd geschrieben wird.

      • Nächster PC: Der zweite Addierer berechnet das Sprungziel, PCSrc wählt den nächsten PC.

      Alle Multiplexer sind eine einzige Zeile mit dem Bedingungsoperator aus Kapitel 24, zum Beispiel alu_b = alu_src ? imm : rd2. Und die Sprungentscheidung mit der Erweiterung für bne ist die Formel aus Kapitel 17:

      \[PCSrc = Branch \cdot (Zero \oplus inst_{12})\]

      Im ganzen Modul gibt es nur einen einzigen always-Block: den PC. Zusammen mit der Registerdatei und dem Datenspeicher ist er der einzige Teil der CPU, der etwas speichert. Alles andere ist kombinatorische Logik zwischen zwei Taktflanken - genau das bedeutet „Single-Cycle“.

      Der PC hat einen synchronen Reset: Solange rst = 1 ist, wird der PC an jeder steigenden Flanke auf 0 gesetzt. Ohne Reset würde der PC mit x starten, und die CPU würde einen Befehl von einer unbekannten Adresse holen.

      Simulation ist (noch) keine Hardware

      Unsere CPU funktioniert - in der Simulation. Können wir sie jetzt auf ein FPGA laden? Wir haben es mit dem Lattice iCE40 HX1K versucht, dem FPGA auf dem Nandland Go Board, das wir im nächsten Kapitel verwenden. Das Ergebnis: Der Entwurf braucht mehr als dreimal so viele Logikzellen, wie der Chip hat.

      Der Grund liegt in den Speichern. Registerdatei und Datenspeicher werden kombinatorisch gelesen. Das FPGA hat schnellen Block-RAM, aber Block-RAM lässt sich nur an einer Taktflanke lesen. Also baut das Synthesewerkzeug unsere Speicher aus einzelnen Flipflops und riesigen Multiplexern - mehr als 3000 Flipflops allein zum Speichern. In der Simulation macht das überhaupt keinen Unterschied.

      Wie man das behebt und was zwischen dem Verilog-Code und dem Chip passiert - Synthese, Place and Route, Timing-Analyse -, ist das Thema von Kapitel 27.

      Selbst ausprobieren

      1. slt hinzufügen. Die ALU kann slt bereits berechnen (ctrl = 0111), aber die ALU-Steuerung kennt den Befehl noch nicht. slt ist ein R-Typ-Befehl mit funct3 = 010. Eine zusätzliche Zeile in alu_control.v genügt. Teste es mit einem kleinen Programm, zum Beispiel:

        00300093  // addi x1, x0, 3
ffb00113  // addi x2, x0, -5
0020a1b3  // slt  x3, x1, x2     3 < -5 ?  -> x3 = 0
00112233  // slt  x4, x2, x1    -5 <  3 ?  -> x4 = 1
00000063  // beq  x0, x0, 0

        Die negative Zahl zeigt, ob der Vergleich wirklich vorzeichenbehaftet ist.

      2. Ein anderes Programm. Ändere program.hex so, dass die CPU die Zahlen von 1 bis 10 aufsummiert und die Summe (55) in memory[8] ablegt. Du brauchst dafür ein Register und ein add mehr. Den Maschinencode kannst du von Hand mit den Formaten aus Kapitel 15 erstellen oder mit einem Assembler, etwa dem im Simulator Ripes.

      3. Absichtlich kaputt machen. Ändere in cpu.v bei der Instanz von alu_control Bit 30 in Bit 29, oder vertausche zwei Eingänge eines Multiplexers. Welche Testbench findet den Fehler? Wie schnell findest du ihn in der Waveform? (Tipp zu Bit 29: Enthält unser Zählprogramm ein sub? Ein Test kann nur Fehler in dem finden, was er auch benutzt.)

      Zusammenfassung

      • Wir haben die Single-Cycle-CPU aus Teil 2 in Verilog gebaut, aus vier Arten von Blöcken: Registerdatei, ALU, Steuerung (Hauptsteuerwerk, ALU-Steuerung, Immediate-Generator) und Speicher.

      • Jeder Block hat seine eigene Testbench bekommen, bevor er verwendet wurde. Die CPU-Testbench musste dann nur noch die Verdrahtung prüfen.

      • Neue Sprachmittel: Arrays (reg [31:0] regs [0:31]), der Reduktionsoperator (~|result), die Replikation ({20{inst[31]}}), $readmemh zum Laden von Speicherinhalten und hierarchische Namen in Testbenches.

      • Die CPU führt unser Zählprogramm in 33 Takten aus - genau wie wir es in Kapitel 17 von Hand vorhergesagt haben.

      • Was in der Simulation funktioniert, passt nicht automatisch auf einen Chip. Darum geht es im nächsten Kapitel.
