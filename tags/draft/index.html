      Introduction and Overview

      Each topic in this course is divided into two parts: one focusing on the mathematical side of digital logic— ideally independent of implementation details— and another more concrete part dealing with those very details. In the concrete part, we will mostly discuss implementations on the electrical level, although other solutions are possible, such as those based on fluid dynamics or optical gates.

      Finite State Machines

      In the post about sequential logic we already briefly met the Mealy and the Moore automata. In the last post we then got to know the building blocks we need to actually build them: flip-flops and registers. In this post the author wants to put both together and show how a finite state machine (FSM) is designed - from the idea, over the state diagram, down to the circuit.

      Why do we need this? Because state machines are everywhere: in every traffic light, in every vending machine, in every protocol like UART or SPI - and, as we will see at the end, in the control unit of a CPU.

      What is a finite state machine?

      A finite state machine is a circuit which can be in exactly one of a finite number of states at any point in time. It consists of:

      1. a set of states, one of them being the start state

      2. the inputs x

      3. the outputs z

      4. the next-state function δ, which determines the next state from the current state and the inputs

      5. the output function λ, which determines the outputs

      In hardware, this looks as follows:

      The green blocks are combinational logic, as we know it from part 1. The blue block is the state register, built from D-flipflops, as described in the last post. With every clock edge the register takes over the next state q' calculated by δ. The current state q is fed back to δ - this feedback is what gives the circuit its memory.

      The dashed connection from the input x directly to the output logic λ only exists in Mealy machines. This brings us to the difference between the two types.

      Mealy vs. Moore

      The Moore machine is the more robust variant: its outputs only change with the clock edge and are stable for a whole clock cycle. The Mealy machine reacts faster and often needs fewer states, but its outputs can produce short spikes (glitches), if the inputs change in the middle of a clock cycle.

      A special case of the Moore machine is the Medvedev machine: here the outputs are directly the outputs of the state register, the output function λ is omitted completely. A synchronous counter, whose outputs are simply its counter bits, is such a Medvedev machine.

      From the idea to the circuit

      The design of a state machine always follows the same steps:

      1. describe the behaviour and draw the state diagram

      2. derive the state table from the diagram

      3. choose a state encoding, i.e. assign a bit pattern to every state

      4. derive the boolean equations for the next state and the outputs

      5. implement the equations with gates and D-flipflops

      The steps 4 and 5 are exactly what we did in part 1 with boolean algebra. Let’s see this using an example.

      Example 1: A traffic light (Moore)

      A German traffic light cycles through four phases: red, red-yellow, green, yellow - and then back to red. Each phase becomes a state, the three lamps red ®, yellow (Y) and green (G) are the outputs. Since the lamps only depend on the current phase, this is a classical Moore machine.

      The next state

      Looking at the columns \(Q_1 Q_0\) and \(Q_1' Q_0'\), we see that the machine simply counts upwards: 00, 01, 10, 11, 00, …​ The equations are:

      \[Q_0' = \overline{Q_0}\]

      \[Q_1' = Q_1 \oplus Q_0\]

      So we need just one inverter and one XOR gate. In contrast to the asynchronous counter of the last post, here both flipflops are clocked by the same clock signal - this is a synchronous counter.

      The outputs

      The output equations can be read directly from the table:

      \[R = \overline{Q_1}\]

      \[Y = Q_0\]

      \[G = Q_1 \cdot \overline{Q_0}\]

      Red is on in both states with \(Q_1 = 0\), yellow in both states with \(Q_0 = 1\), and green only in state S2. The whole traffic light therefore consists of two D-flipflops, two inverters, one XOR and one AND gate.

      The well-chosen encoding is no coincidence: with another assignment of bit patterns to the states the equations would become longer. The choice of the state encoding has a direct influence on the size of the circuit.

      Note
      		Real traffic lights stay in the green phase much longer than in the red-yellow phase. For this, the machine gets an additional input T (time elapsed) from a timer: as long as T = 0, the machine stays in its current state. In hardware this is a multiplexer in front of each flipflop, which chooses between the current state q and the next state q'.

      Example 2: A sequence detector (Mealy and Moore)

      The difference between Mealy and Moore can best be seen with a second example. Our machine receives one bit x per clock cycle and should output z = 1, whenever the bit sequence 101 has been received. Overlapping sequences count too: the input 10101 contains the sequence twice.

      State encoding

      In the traffic light example we simply numbered the states as binary numbers. There are other variants:

      Encoding

      Example for 4 states

      With one-hot encoding exactly one flipflop is set per state. This needs more flipflops, but the logic for the next state and the outputs often becomes very simple. Since FPGAs have plenty of flipflops, synthesis tools often choose this encoding automatically.

      Pitfalls

      There are a few things to watch out for:

      1. Reset: After switching on, the flipflops contain random values. A reset signal is needed, which puts the machine into a defined start state.

      2. Unused states: The Mealy sequence detector has three states, but two flipflops can store four. The unused pattern 11 must lead back to a valid state - otherwise the machine might get stuck there forever.

      3. Asynchronous inputs: If an input (e.g. a push button) is not synchronized to the clock, it can change just at the clock edge and put the flipflop into an undefined (metastable) state. The remedy is a synchronizer consisting of two flipflops in series in front of the machine.

      Outlook: The control unit as a state machine

      In the post about the data path we will see that every instruction passes through the phases fetch, decode, execute, memory access and write back. In a multi-cycle CPU, which uses one clock cycle per phase, the control unit is exactly such a state machine: every phase is a state, and the outputs are the control signals for multiplexers, ALU, register file and memory. The opcode of the instruction is the input which determines, which state follows.

      In our first CPU we take the simpler path: in a single-cycle CPU all phases are executed in one clock cycle, and the control unit becomes pure combinational logic. We will look at this in the chapter about the control unit.

      Further reading: David Money Harris and Sarah L. Harris, 'Digital Design and Computer Architecture - RISC-V Edition', chapter 3, covers state machines in detail.

      RISC-V: The Instruction Set

      Digital design meets computer architecture

      So far we have looked at the individual building blocks of a processor: logic gates, adders and the ALU in part 1, and flip-flops, registers and memory in part 2. In the next three chapters we combine these building blocks into a simple CPU. But first we have to decide which instructions this CPU should understand at all. This decision is called the instruction set architecture (ISA). It is the interface between software and hardware: the programmer (or compiler) only sees the instructions, and the hardware has to be able to execute them.

      The Data Path

      In the last chapter we got to know the RISC-V instruction set and wrote a first program. Now it is about the hardware: how does a CPU have to be built, so that it can execute these instructions? For this we combine the building blocks from the previous chapters - ALU, registers and memory - into a data path.

      A minimal implementation

      The minimal working subset of a RISC-V implementation contains the following instructions:

      • the arithmetic-logical instructions add, sub, and and or [R-type]

      • the memory instructions load word (lw) and store word (sw) [I-type and S-type]

      • the conditional branch instruction branch if equal (beq) [B-type]

      We will see how the chosen instruction set architecture affects key performance aspects such as clock rate and cycles per instruction (CPI). We will also see that the different instruction types only differ in the later phases of execution.

      For every instruction the first two steps are identical:

      1. The program counter (PC) holds the address of the current instruction. This address is sent to the instruction memory, which returns the instruction.

      2. One or two registers are read from the register file; the register numbers are contained in the fields of the instruction. lw and addi read only one register (rs1), all other instructions in our subset read two (rs1 and rs2).

      The next steps depend on the instruction type, but still use the same resources. R-type instructions use the ALU to compute the result, memory instructions use it to compute the address, and branch instructions use it for the equality test. Only after the ALU do the different instruction types really differ.

      This abstract schematic does not explain all cases yet, however: for example, it does not show how the ALU knows which operation to perform, or when the register file is written. For that we need an extended schematic that also shows the control.

      The execution phases for the different instruction types

      We start with the five classic phases of a RISC processor and show what happens in each phase for typical instructions:

      So in the fetch phase, every instruction initially only computes PC + 4. Whether a branch is taken instead is only known for beq after the ALU has compared the two registers. A multiplexer then selects between PC + 4 and the branch target as the new value of the program counter.

      In our first, simple implementation all five phases are completed within a single clock cycle (single-cycle processor). Splitting execution into phases still helps understanding – and it is the foundation of pipelining, where several instructions are processed in different phases at the same time.

      The instruction part

      To explain a CPU on this abstract level, we need a few more concepts. An instruction is stored in memory and is accessible under a specific address. An address in RISC-V (in its 32-bit variant RV32) is a 32-bit value pointing to a specific byte in memory. The program counter (PC) is a register that holds the address of the current instruction in instruction memory. The program counter is connected to the first adder, which adds the constant 4 to it: an instruction is 32 bits = 4 bytes long, so the next instruction is located 4 addresses further on.

      If the instruction is a branch instruction, a second adder adds the offset contained in the instruction to the program counter. This is how jumps are created: if the branch condition is met, this result is loaded into the program counter instead of PC + 4.

      The data part

      The data path shows elements we are already familiar with: the ALU and the two memory blocks – the register file on the left and the data memory on the right. The first input of the ALU is connected to the first read port of the register file (rs1). The second input receives either the value of the second read port (rs2) or a constant from the instruction, such as the offset for lw and sw. Depending on the instruction, the ALU result is used as the value for the register file or as the address for data memory; for lw, the value read from data memory is written back to the register file.

      The control part

      So far, the control part is the most black-boxed element in our schematics. We already know how multiplexers work, and we can already see the feedback path through which a branch affects the program counter. What is still open is the central question: how do the multiplexers, the ALU, the register file and the data memory know what to do for a particular instruction? The answer is the control unit, which derives the appropriate control signals from the instruction’s opcode.

      How the control unit works is shown in the next chapter: The Control Unit. There we also trace our example program clock cycle by clock cycle through the CPU.

      The Control Unit

      At the end of the post about the data path one question remained open: how do the multiplexers, the ALU, the register file and the data memory know what to do for a particular instruction? In this post the author wants to answer this question by building the last missing piece of our CPU - the control unit.

      In the post about finite state machines we have seen that the control unit of a multi-cycle CPU is a state machine. Our first CPU is a single-cycle CPU, which executes every instruction within one clock cycle. Here the control unit needs no state at all: it is pure combinational logic, as we know it from part 1. Its input is the instruction, its outputs are the control signals.

      Let’s go through the rows:

      • R-type: both operands come from registers (ALUSrc = 0), the ALU result (MemToReg = 0) is written into rd (RegWrite = 1). The ALU operation results from funct3 and funct7 (ALUOp = 10).

      • lw: the ALU adds the base register and the offset (ALUSrc = 1, ALUOp = 00), the data memory is read (MemRead = 1) and the value read is written into rd (MemToReg = 1, RegWrite = 1).

      • sw: the address is calculated like for lw, but rs2 is written to the data memory (MemWrite = 1).

      • beq: the ALU subtracts rs2 from rs1 (ALUOp = 01). If the result is zero, both registers are equal and the branch is taken (Branch = 1).

      From the table to the gates

      How do we turn this table into a circuit? The easiest way is a decoder - as in our excursion about decoders - which recognizes the four opcodes and activates exactly one of the four lines R, LW, SW and BR. Then every control signal is simply an OR of the lines in which it is 1:

      \[RegWrite = R + LW\]

      \[ALUSrc = LW + SW\]

      \[MemToReg = MemRead = LW\]

      \[MemWrite = SW\]

      \[Branch = BR\]

      \[ALUOp_1 = R \qquad ALUOp_0 = BR\]

      So the complete main control consists of a decoder for 7 bits and two OR gates. In real processors this is often implemented as a PLA (programmable logic array) or simply described in a hardware description language and left to the synthesis tool.

      Why two stages? The main control only has to make a rough decision ("address calculation", "comparison" or "look at funct"), and the ALU control does the fine decoding. Both blocks remain small, and each of them has only a few inputs. This principle of multi-level decoding keeps the logic small and fast.

      The immediate generator

      Some instructions contain a constant (immediate). The immediate generator extracts it from the instruction bits and extends it to 32 bits. Depending on the format, the bits are located at different positions:

      Format

      That looks a bit confusing at first, but it has a reason: wherever possible, a bit of the constant is located at the same position in all formats. And the sign bit is always inst[31]. This way the sign extension can start immediately, before the format is even known.

      For branches, the lowest bit imm[0] is always 0, since branch targets are always at an even byte address. It is therefore not stored in the instruction at all - this doubles the range of the branch.

      The sign extension fills the upper bits with copies of the sign bit. This way, a negative offset like -8 remains negative after the extension (two’s complement says hello).

      The branch decision

      For a branch the ALU computes rs1 - rs2. Its Zero output is 1, if the result is 0 - i.e. if both registers are equal. At the same time, the second adder calculates the branch target PC + offset. The multiplexer in front of the PC is controlled by:

      \[PCSrc = Branch \cdot Zero\]

      Only if the instruction is a branch and the registers are equal, the branch target is loaded into the PC. In all other cases the PC simply moves on to PC + 4.

      One instruction on its way through the CPU

      Let’s follow the instruction lw x5, 8(x6) through the picture above:

      1. The PC sends the address of the instruction to the instruction memory, which returns the instruction. At the same time, the first adder calculates PC + 4.

      2. The control unit recognizes the opcode 0000011 and sets RegWrite = 1, ALUSrc = 1, MemToReg = 1, MemRead = 1, MemWrite = 0, Branch = 0 and ALUOp = 00.

      3. The register file reads x6 (rs1). The immediate generator delivers the constant 8.

      4. Since ALUSrc = 1, the ALU receives x6 and 8. The ALU control sees ALUOp = 00 and selects addition.

      5. The ALU result x6 + 8 is the address for the data memory, which delivers the word stored there.

      6. Since MemToReg = 1, this word arrives at "Write data" of the register file.

      7. Branch = 0, so PCSrc = 0, and PC + 4 is waiting at the input of the PC.

      All of this happens within one clock cycle, as pure combinational logic. Only with the next rising clock edge, the new values are taken over: the register file writes x5, and the PC takes over PC + 4. This is exactly the behaviour of the D-flipflops from the post about clocks and registers.

      Extending the CPU: addi and bne

      Our example program from the RISC-V post uses two instructions which our minimal CPU cannot execute yet: addi and bne. Let’s extend the CPU - this shows nicely how the control unit grows with the instruction set.

      addi

      addi has its own opcode 0010011 and the I-format, like lw. It needs the constant as second ALU operand (ALUSrc = 1) and writes the ALU result into rd (MemToReg = 0, RegWrite = 1). The decoder gets a fifth line IMM:

      \[RegWrite = R + LW + IMM\]

      \[ALUSrc = LW + SW + IMM\]

      But which ALUOp? One might think of ALUOp = 10 (look at funct), since funct3 = 000 for addi. But this would be a trap: with addi there is no funct7 field - the upper bits belong to the constant. For addi x5, x5, -1 the constant consists only of ones, so bit 30 is 1 as well, and the ALU control would select subtraction! x5 - (-1) would give x5 + 1 instead of x5 - 1. So we choose ALUOp = 00, and the ALU always adds.

      bne

      bne has the same opcode as beq (1100011), they only differ in funct3: 000 for beq and 001 for bne. The lowest bit of funct3 (inst[12]) thus tells us whether the branch should be taken on equality or on inequality. We extend the branch decision by an XOR gate:

      \[PCSrc = Branch \cdot (Zero \oplus inst_{12})\]

      For beq (inst[12] = 0) the Zero signal passes unchanged, for bne (inst[12] = 1) it is inverted. The XOR works here as a controllable inverter - a trick we will meet again and again.

      And the j?

      Our program ends with j done, a pseudo instruction for jal x0, done. jal would need another opcode and an additional path for writing PC + 4 into rd. But we don’t need it: beq x0, x0, done has exactly the same effect, since x0 is always equal to itself. The branch is therefore always taken.

      Our example program, clock by clock

      With these extensions, our CPU can now execute the example program. The program is located from address 0x00 on:

      0x00:        addi x1, x0, 0       # x1 = 0   (counter)
0x04:        addi x2, x0, 1       # x2 = 1   (step)
0x08:        addi x3, x0, 10      # x3 = 10  (end value)
0x0C: loop:  add  x1, x1, x2      # x1 = x1 + x2
0x10:        sw   x1, 4(x0)       # memory[4] = x1
0x14:        bne  x1, x3, loop    # while x1 != x3: jump to loop (offset -8)
0x18: done:  beq  x0, x0, done    # endless loop (offset 0)

      Outlook

      This is where the series ends for now - but this is exactly where computer architecture really starts. Here are the most important next steps, which you will find in the literature:

      • Multi-cycle CPU: every phase gets its own clock cycle, and an instruction only uses as many cycles as it needs. The control unit becomes a state machine - exactly as described in the post about finite state machines.

      • Pipelining: the phases are separated by registers, and up to five instructions are processed at the same time, like on an assembly line. In the ideal case one instruction finishes every 200 ps instead of every 800 ps.

      • Hazards: with pipelining, problems arise: an instruction needs a result that is not yet written back (data hazard), or it is not clear yet whether a branch will be taken (control hazard). Forwarding and branch prediction help here.

      • Caches: real main memory is much slower than 200 ps. Small, fast buffer memories close to the CPU hide this.

      • Interrupts and exceptions: the CPU must be able to interrupt the current program, e.g. when a key is pressed or a division by zero occurs.

      If you want to build the CPU yourself, a hardware description language and an FPGA are the next step. The author has written some posts about getting started with FPGAs.

      Conclusion

      From the first logic gate to a CPU that runs a program: this was the path of this series. In part 1 we got to know the combinational building blocks - gates, boolean algebra, adders and the ALU. In part 2 the memory was added - flipflops, registers, memory and state machines - and finally all of this was combined into a working RISC-V CPU.

      Hardware Description Languages (HDLs) and their use in modern digital design development

      In the first two parts of this series we designed a complete CPU - from the single logic gate up to the control unit. We did this the classical way: with truth tables, boolean equations and schematics. For a full adder or a 4-bit counter this works well. But a modern processor consists of billions of transistors, and nobody draws billions of transistors by hand.

      This is where Hardware Description Languages (HDLs) come in. An HDL describes a circuit as text: which signals exist, how they are connected and how the circuit behaves. At first glance, HDL code looks like a program in an ordinary programming language - but it is something fundamentally different. A program describes a sequence of steps that a processor executes one after another. An HDL describes hardware, in which all parts work at the same time.

      The same HDL description serves several purposes:

      • Documentation: the description is precise and can be read by humans and machines.

      • Simulation: we can test the circuit on the computer before it physically exists.

      • Synthesis: tools translate the description automatically into gates and flip-flops - for an FPGA or for a custom chip (ASIC).

      In this part of the series we use exactly this workflow: we describe the circuits from parts 1 and 2 in an HDL, test them in simulation and look at how they finally become hardware.

      Simulation and Testbenches

      In the last chapter we saw that an HDL description can be used for documentation, simulation and synthesis. In this chapter we look at simulation - and at the question of how we can be sure that a circuit does what it should, before it even exists.

      Why is this so important? With software, a bug can be fixed with a new release. With hardware it is different: a faulty chip that has already been manufactured cannot be patched, a new manufacturing run (a so-called respin) costs a lot of money and months of time. Even with FPGAs, which can be reprogrammed, debugging on the real hardware is tedious, since we can only observe the few signals that are connected to a pin. In a simulation, on the other hand, we can see every signal at every point in time.

      That is why in chip development often more effort goes into verification than into the design itself.

      How a simulator works

      A simulator does not execute the circuit like a program, line by line. Instead, it simulates the behaviour of the hardware over time. Most HDL simulators work event-driven:

      1. The simulator manages a simulation time, which has nothing to do with the real time on the computer.

      2. Whenever a signal changes, this is an event.

      3. The simulator then re-evaluates all parts of the circuit that depend on this signal. This can trigger new events, which are processed in turn.

      4. When there are no more events at the current point in time, the simulator jumps to the next point in time at which something happens.

      This is how the simulator reproduces the fact that in real hardware all parts work at the same time: every gate reacts to its inputs, no matter in which order it appears in the source code.

      Four values instead of two

      In part 1 a signal was either 0 or 1. A Verilog simulator knows four values:

      Value

      Meaning

      0

      logical zero

      1

      logical one

      x

      unknown - e.g. a flip-flop that has not been reset yet, or two drivers working against each other

      z

      high impedance - the signal is not driven at all (e.g. a tri-state output that is switched off)

      The value x is very useful when debugging: if a signal shows x in the simulation, something is not initialized or not connected - a mistake that would lead to random behaviour in real hardware.

      The testbench

      To simulate a circuit, we need someone who applies values to its inputs and looks at its outputs. In the laboratory this would be a signal generator and an oscilloscope. In the simulation this job is done by a testbench - another Verilog module that surrounds the circuit to be tested, the device under test (DUT):

      A testbench typically consists of:

      • Stimulus: generates the input values for the DUT - and, for sequential circuits, the clock and the reset.

      • DUT: the circuit we want to test. It is used inside the testbench exactly as it would be used in a larger design.

      • Reference model and checker: compute the expected values and compare them with the actual outputs of the DUT.

      In contrast to the DUT, the testbench itself has no inputs and outputs - it is the complete "world" in which the DUT lives. It also doesn’t need to be synthesizable: it may use delays, loops and text output, which do not exist in real hardware.

      Let’s go through the most important parts:

      • `timescale 1ns / 1ps: one time unit in this file is 1 ns, the simulator calculates with a precision of 1 ps.

      • reg and wire: the testbench drives the inputs of the DUT itself, so they are declared as reg. The outputs are only observed, so they are wire signals.

      • Instantiation: full_adder dut (…​) inserts the full adder into the testbench. .a(a) connects the port a of the full adder with the signal a of the testbench.

      • initial: a block that runs exactly once at the start of the simulation - it only exists in simulation.

      • {a, b, cin} = i: the three inputs are combined into a 3-bit number, so the loop counts through all combinations from 000 to 111.

      • #10: wait 10 time units, i.e. 10 ns. Only now does the simulator calculate the outputs of the DUT.

      • $display, $dumpfile, $dumpvars, $finish: system tasks of the simulator for text output, for recording the waveform and for ending the simulation.

module full_adder_tb;
    reg  a, b, cin;
    wire sum, cout;
    integer i;
    integer errors = 0;

    full_adder dut (.a(a), .b(b), .cin(cin), .sum(sum), .cout(cout));

    initial begin

            {a, b, cin} = i;
            #10;
            // reference model: the sum of three bits is a 2-bit number
            if ({cout, sum} !== a + b + cin) begin
                $display("ERROR: a=%b b=%b cin=%b -> got %b%b", a, b, cin, cout, sum);
                errors = errors + 1;
            end
        end
        if (errors == 0) $display("PASSED: all 8 combinations correct");
        else             $display("FAILED: %0d errors", errors);
        $finish;
    end
endmodule

      The operator !== compares including the values x and z - an output that is x is reported as an error. If we build in a mistake on purpose, e.g. cout = (a & b) | (cin & a), the testbench finds it immediately:

      ERROR: a=0 b=1 cin=1 -> got 00
FAILED: 1 errors

      Testing all combinations (exhaustive testing) is only possible for small circuits. For a 32-bit ALU with two operands there are \(2^{64}\) combinations - even at a billion tests per second, this would take more than 500 years. In practice, we therefore combine:

      • corner cases: 0, 1, the largest and smallest value, overflow, all bits set, …​

      • random tests: many randomly generated inputs, which are checked against the reference model.

      • directed tests: specifically constructed sequences that exercise a certain function.

      Verification and test - two different things

      Finally an important distinction. Everything we did in this chapter is verification: we check whether our design is correct. But even a correct design can fail in the real world: during manufacturing of a chip, a tiny particle of dust can break a connection or short two wires. Finding such manufacturing defects is the job of testing.

      So that a finished chip can be tested at all, testability has to be planned into the design from the beginning (design for testability). Two common techniques:

      • Scan chains: in a special test mode, all flip-flops of a chip are connected to form one long shift register. This way, arbitrary states can be shifted in and the results shifted out - every flip-flop becomes accessible from the outside.

      • Boundary scan (JTAG): a standardized interface (IEEE 1149.1), with which the pins of a chip can be controlled and read from the outside, for example to test the solder joints on a circuit board. Today JTAG is also the usual interface for programming and debugging microcontrollers and FPGAs.

      Summary

      • A simulator reproduces the behaviour of hardware over time, event by event.

      • A testbench surrounds the device under test, generates the input values and checks the outputs.

      • Self-checking testbenches with a reference model find errors automatically.

      • Waveforms show every signal at every point in time - the most important tool for debugging.

      In the next chapter we use these tools to describe the combinational circuits from part 1 in Verilog - and of course to test them right away.
